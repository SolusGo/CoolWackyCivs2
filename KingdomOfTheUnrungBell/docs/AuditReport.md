## Combat alternatives investigated

The pinned official CP v151 source is `44c1e14ff75d80c1dba5c8a71e8289439a53aafb`. `SourceAudit.json` retains URLs/hashes and 44 executable contracts, including attack/defense plot arguments, both upgrade event phases, city lifecycle mutations and owner-turn/autosave order.

`FriendlyLandsModifier` adds into the ordinary modifier accumulator. Melee attacks pass the target plot and defense passes the defended plot. `IsFriendlyTerritory` includes the player's team and territory accessible through open borders, including qualifying city-state access. Ranged strength checks the firing unit's plot, not its target. Bellwarden/Toll remain additive; `FriendlyLandsAttackModifier` and generic `CombatPercent` remain zero. The exact Kingdom-owned target rule is therefore still not met.

The audit reviewed loaded promotion fields for territory, ownership, generic strength, nearby cities and city attack/defense. Neither those fields nor terrain/feature effects supply an exclusively player-owned battle-plot predicate. Movement/ownership events cannot supply the hypothetical target for combat previews or ranged attacks. Unit strength Lua bindings expose native calculations, rather than a per-calculation ownership-filter return hook.

`BattleStarted` and `BattleJoined` run during combat generation. Installed Firaxis `EnemyUnitPanel.lua` independently queries attack, defense and ranged strength for previews. Toggling generic strength promotions around battle events would therefore omit or misrepresent previews, and introduce abort/reentrancy cleanup hazards. `CombatResult` receives already-calculated damage; `CombatEnded` is later still. Damage-delta callbacks do not implement an additive strength modifier while preserving the ordinary calculation. No supported safe exact alternative was found. Retain the native approximation, disclose it in Civilopedia and guides, and introduce no DLL or transient generic-bonus workaround.

## Persistence evidence and its limits

Installed Firaxis scenario code opens `Modding.OpenSaveData()` once and uses dot-call `GetValue`/`SetValue` to distinguish first initialization. The installed `Civ5SavedGameDatabase.db` has a `SimpleValues(Name TEXT Primary Key, Value VARIANT)` table. Only its schema was read; no installed save or database was modified.

The [TableSaverLoader author's save integration explanation](https://forums.civfanatics.com/threads/tablesaverloader-for-persisting-lua-table-data-through-game-save-load.442249/) describes packing this database into the save container. A [direct developer test](https://forums.civfanatics.com/threads/saveutils-lua-itemized-data-storage-across-mods.392958/page-10) retrieved stored values after quitting, clearing cache and loading the save. These support the API contract, rather than constituting a native test of this civilization. No user-store or generated-game-ID migration is justified.

The executable owns database packing/restoration and UI event delivery; those internals are not supplied in the CP source. Current-machine quick-save/quick-load, multiple slots, older saves and end-turn autosave replay still require native acceptance. The controller already writes every authoritative change immediately, so it does not need UI save-button interception. `MapModData` stores callback ownership only; valid progression is never reconstructed from its globals. Fresh contexts reopen the save connection and retire stale callbacks.

## Results and remaining risks

Ten shipped-controller Lua 5.1 suites pass, including the four new suites. SQL/schema, original and changed-baseline inheritance, localization references, XML, all 48 DDS decodes/mips/atlas slots, human-only flags and source contracts pass. Collection checks and package verification are run as part of this refinement. These are file/source/model tests; **no native Civ V gameplay or save round trip was performed**.

Ready for native acceptance using [NativeAcceptance.md](NativeAcceptance.md). Highest priorities are native save rollback/end-turn boundary replay and synchronous war-notification delivery. Native city-yield refresh, preview/damage behavior and upgrade retention follow. Existing documented API-failure recovery can leave effects stale until a native setter recovers; corrupt/newer records stay preserved with conditional effects disabled. Exact exclusively owned-target combat remains an acknowledged engine limitation, not a newly introduced regression. No significant new gameplay blocker was found beyond that deviation and pending native verification.
