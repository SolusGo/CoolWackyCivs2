# Implementation and engine evidence

## Database compatibility

The five SQL actions retain their original contiguous position; newer civilizations may append afterward. Existing Type identities, ID insertion order, collection UUID and save compatibility version are retained. Selection is human-only, but the controller does not test `IsHuman()`. The trait is empty: Washington's abilities are not inherited. Only ordinary free-start civilization relationships and the three supported leader personality tables are copied. Maren favors naval defense, Science and Culture; these are AI preferences, not victory modifiers.

The generator reads the installed v151 schema. Shipped SQL uses temporary `SELECT *` tables at **activation**, so active Trireme/Lighthouse properties, including future compatible scalar columns, are copied rather than freezing the fixture's vanilla values. It copies every available Unit*/Building* companion table with the owning UnitType/BuildingType column, including normal promotions, upgrade classes, resource requirements, flavors, sea-resource yields, prerequisites and CP extension tables. The ordinary Trireme model and Lighthouse appearance are retained. No original unit or building row is updated.

The local fixture is a read-only BNW snapshot with v151 schema overlaid in memory, **not proof of a live activated CP economy**. An altered-baseline test changes Combat/Movement/Cost, adds unknown scalar columns and resource requirements, and supplies preexisting Lighthouse Culture to verify active inheritance and exactly +1 additive Culture. No baseline Lighthouse bonuses are copied twice.

`PROMOTION_LANTERN_FRIENDLY_WATERS` sets VisibilityChange=1 and FriendlyLandsModifier=15, CannotBeChosen=1, LostWithUpgrade=0. Only the Cutter receives it. Ordinary promotion retention therefore keeps this training on upgrades; other inherited promotions retain their own normal rules. There is no generic CombatPercent or outside-friendly modifier.

At pinned CP commit `44c1e14ff75d80c1dba5c8a71e8289439a53aafb`, CvPromotionClasses.cpp reads those actual columns. CvUnit.cpp's `GetMaxAttackStrength` and `GetMaxDefenseStrength` both call `GetGenericMeleeStrengthModifier`, which adds `getFriendlyLandsModifier()` only when the battle plot passes `IsFriendlyTerritory(owner)`. For an attack the battle plot is the destination; for defense it is the defending plot. The ranged path also honors the native field if retained on a later ranged upgrade. CvPlot.cpp defines friendly territory as own/team land, major territory granting open borders, and eligible city-state open borders. Unowned/enemy territory receives no Lantern Strength. This is native friendly territory, not an invented own-territory-only check. Native combat displays and upgrades still require acceptance testing.

## Qualification and state

One invisible InGameUIAddin XML owns all gameplay subscriptions. A generation-aware MapModData context guard prevents duplicate registration, retires the old implementation even when included in the same context, and retires old contexts; globals do not hold economic state. There are no movement, dirty-event, frame, load-screen or construction subscriptions in the controller.

`city:IsCoastal(-1)` calls native `CvCity::isCoastal`, which forwards to `plot()->isCoastalLand(iMinWaterSize)`. Its default -1 uses the engine's ordinary ocean-size threshold. Only `city:Plot():GetUnit(index)` is inspected. A ship must match the actual city owner, have DOMAIN_SEA, pass IsCombatUnit, and be non-embarked, living and not delayed-death. All city decisions (including Lighthouse presence) are frozen before any dummy writes.

`BUILDING_LANTERN_GUARDED_HARBOR` supplies exactly Science 2/Culture 1; `BUILDING_LANTERN_SIGNAL_GOLD` supplies exactly Gold 2. Each has a separate ordinary building class, IsDummy=1, ShowInPedia=0, GreatWorkCount=-1, Cost/FaithCost=-1, NeverCapture=1, ConquestProb=0 and zero maintenance/other effects. The setter assigns real counts **0 or 1**, never increments.

The compatible `[LANTERN1|gameTurn]` receipt now means **completed**, written only after every applicable dummy count was verified. New `[LANTERN2|settledTurn|intentTurn|mode|targets]` metadata holds phase (`N` none, `R` reserved/incomplete, `S` frozen) and immutable city targets. Each target records coordinates, native city ID, founding turn, two binary counts and a capture cancellation bit. All targets are saved and acknowledged before the first positive building write. An unacknowledged intent may be buffered in the current context, but it must be durably acknowledged in player ScriptData before building recovery can apply it. Native building counts remain the only economic effect.

Retries use saved targets, never current ship positions or current Lighthouse presence. A setter that throws after successfully changing its count is acknowledged by readback. Two immediate bounded attempts handle transient errors; persistent failures retain the journal, including across context recreation and full Lua VM restart. Duplicate start notifications may finish a journal, then stop at the completion receipt. Reservations interrupted before complete qualification cannot reconstruct the missing past state and never rescan that turn. Logs identify player/turn/phase and city/building/target for failed building writes.

A source-verified late **PlayerDoTurn observer** records the settled phase only. It scans no ships, changes no buildings and pays no yields. Status callbacks arriving after this observed boundary are rejected instead of becoming a convenient late snapshot. This catches one bad ordering; it cannot prove that callbacks before the observer also precede every individual economic calculation.

Fresh initial/scenario admission uses the engine's loaded-game flag (`UI:IsLoadedGame()`, used by Firaxis LoadScreen.lua for Begin versus Continue) and native `Game.GetStartTurn()`. An active owner on a fresh initial turn is no longer pre-stamped complete. Loaded/progressed active owners without current receipts are conservatively phase-sealed; ordinary loads preserve completed counts. Initialization can finish a **saved frozen plan** or a zero-only capture cleanup, with no qualification scan. Missing lifecycle APIs fail closed for ambiguous active bootstrap. Native ordering of these lifecycle flags versus the selected notification remains untested; introducing a controller for the first time *after* economics on the very first fresh turn with no prior phase/receipt is intrinsically ambiguous with the available evidence.

Recovery also checks actual civilization type: an old completed/pending Lantern state on a scenario/debug player changed to another civilization is zero-cleaned, never restored positively.

City capture is not dropped behind the snapshot reentrancy guard. It persistently cancels affected targets, reacquires the city, saves a zero-only `[LANTERN_CLEAR2|identities]` cleanup intent for the actual recipient, and independently attempts both clears. It never changes the Signal Lighthouse itself or consumes the recipient's next snapshot. Cleanup recovery also checks owner, city ID and founding turn; nested captures cannot erase new unacknowledged cleanup intents. NeverCapture/ConquestProb=0 remain native safeguards. No position check occurs on capture.

Known malformed/duplicate receipt blocks are preserved verbatim under `LANTERN_QUARANTINE*` names and an ambiguous active turn is phase-sealed. Newer unknown save versions are preserved and disabled, not downgraded. Unrelated player ScriptData is preserved. Old completed `LANTERN1` saves remain readable; all database IDs, dummy IDs, artwork, numerical values and minimum compatible save version are unchanged. See [Hardening.md](Hardening.md) for limits that a journal cannot solve.

## Turn timing: verified publication, unverified executable dispatch

The selected candidate is **Events.AIProcessingStartedForPlayer**, restricted to untagged turn-start status and an active actual Lantern owner, once per saved game-turn receipt. There is no PlayerDoTurn economic fallback and no direct yield payout; its new observer only records a late phase and diagnoses/rejects late starts.

Verified in the pinned [CvPlayer.cpp source](https://github.com/LoneGazebo/Community-Patch-DLL/blob/44c1e14ff75d80c1dba5c8a71e8289439a53aafb/CvGameCoreDLL_Expansion2/CvPlayer.cpp):

1. `setTurnActive(true)` sets native turn-active state, then publishes `DLLUI->PublishPlayerTurnStatus(TURN_START, GetID())` (line 33986), before the call to `doTurn()` (line 34023).
2. `doTurn()` reaches `doTurnPostDiplomacy()` (diplomacy can defer this continuation).
3. That continuation runs city `doTurn()` (10434), Treasury DoGold (10440), Culture accumulation (10457), `doResearch()` (10497), then PlayerDoTurn (10571).
4. The installed Firaxis `Assets/UI/InGame/TurnProcessing.lua` listens to `Events.AIProcessingStartedForPlayer(iPlayerID, szTag)` and explicitly filters out human players itself. This establishes the event's API, but does **not** prove the executable maps TURN_START to that event synchronously for human players.

The executable's UI publication/dispatch implementation is outside the available DLL source. **Neither mocks nor publication lines prove human delivery or same-turn payout.** During this audit the user explicitly instructed **not to launch Civ V**. No native gameplay/economic test was performed and no launch was retried after that instruction. Before the restriction, the application approval attempt timed out. The selected event's human/scenario-AI delivery, tag/activity assumptions, initial lifecycle ordering and delivery before *all* economic calculations remain native acceptance gates. Current verdict: **STATICALLY VALIDATED, NATIVE ACCEPTANCE PENDING**.
If acceptance shows delayed dispatch or no human notification, this candidate is unsuitable. Do not switch to PlayerDoTurn or owner-end staging, both of which violate the requested turn-start semantics. Find a genuinely earlier available hook or report that the exact mechanic needs an engine hook beyond CP151's exposed simulation events. No DLL modification is included. `ActivePlayerTurnStart` is published after `doTurn()` in this same function; `PlayerDoneTurn` is an end boundary; `PlayerPreAIUnitUpdate` is in the unit-update routine. None establishes a substitute beginning-of-owner-turn economic hook. Global NewGameTurn or frame polling would also change the required semantics.

## Art

Five original built-in imagegen paintings and saved prompts are in `art-source/TheLanternFleet`. The deterministic compiler produces 40 legacy DXT5 DDS textures with complete mip chains: navy/gold civ and leader atlases, object atlases, alpha symbols, unit flag, 1600x900 static leader, 1024x768 Dawn and harbor map illustration. Atlas sizes match the collection (16/24/32/45/48/64/80/128/256), with the same gold framing and portrait padding. There are no missing referenced assets. Static fallback diplomacy, ordinary 3D unit/building models and no voiced dialogue are intentional.
