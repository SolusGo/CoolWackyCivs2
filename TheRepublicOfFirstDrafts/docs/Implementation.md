# Implementation evidence

## Database and inheritance

`00_RFD_Core.sql` creates fresh trait/civ/leader identities, overrides and names. Washington/America supply ordinary scalar presentation/start defaults, with a new trait mapped explicitly; no Washington trait or AI strategy rows are copied. All identifiers use `RFD`.

The unit and building clones use `CREATE TEMP TABLE ... AS SELECT *` at mod activation, reset `ID`, change their identity/presentation, then insert the whole active row. Thus active CP cost, strength, setup-related properties, range, prerequisites, specialist slots, production and other scalar fields are inherited, including schema columns unknown to the generator. `01_RFD_Inheritance.sql` was generated by enumerating the installed CP v151 schema's Unit*/Building* companion tables with `UnitType`/`BuildingType`. It includes `UnitGameplay2DScripts`, free promotions, resource quantities, AI registrations and class upgrades. Primary IDs, where present, are reset; owning identity keys change. Runtime selects read active companion values, not recorded vanilla values. Tables added by unrequested future dependencies after this generated inventory require a new schema audit.

The Ink Mortar changes Moves by exactly one; its additional free promotion has `VisibilityChange=1`, `CannotBeChosen=1`, `LostWithUpgrade=1`. All normal Catapult promotions and its art define are retained. `02_RFD_Effects.sql` increases exactly one inherited Culture row, or inserts one if absent, so even multiple baseline Culture rows total exactly +1.

## Persistence and owner-turn timing

`PlayerDoTurn` is the authoritative possession evaluation. It scans currently owned buildings, maps eligible types to class TYPE names, unions across cities and compares with permanent ScriptData history. Free and real buildings are read through `City:GetNumBuilding`. One saved last-evaluation turn suppresses repeated same-turn callbacks. Building notifications never award UA yields.

The `[RFD1|turn|class,class|journal]` block is sorted and replaced alone, preserving foreign data. The optional journal is `phase,cultureBefore100,cultureTarget100,goldBefore100,goldTarget100`. The class ledger is committed with the journal before payout. Phase 1 reconciles Culture; phase 2 reconciles Gold. Actual native balances must equal the old value or the intended target. Already-target balances are acknowledged without mutation. Successful stages use saved acknowledgements; completion removes the journal. A ScriptData write is read back before continuing. Ambiguous balances or malformed data stop payouts and log an error without deleting the evidence.

No ordinary save is taken inside these synchronous non-yielding Lua callbacks. The journal additionally handles simulated exceptions before/after mutations and failures between stages. It cannot infer whether unrelated later balance changes include an unacknowledged reward; it deliberately fails closed in that exceptional case. This is a limitation of independently persisted game yield/ScriptData writes, not an unsafe increment-only counter.

On initial registration, absent ledgers seed current classes without payout only when current turn exceeds the actual game start turn. Existing ledgers survive context reload and a completely new Lua VM. Advanced starts at their StartTurn remain new games. A late install during that exact first turn is indistinguishable from ordinary new-game initialization and is documented accordingly.

## Dynamic Science and lifecycle

The same eligibility lookup supplies current per-city class sets. Science is `min(3,floor(count/4))` only for living human Republic owners with the UB. The three marker buildings each yield one Science; exact real-building counts 0/1 represent the target. Writes only occur when counts differ. No cumulative yield mutation or shared history count is used.

Production and both purchase currencies publish CP's `CityConstructed`; `CitySoldBuilding` and `SpecificCityInfoDirty` handle sales/other changes when published. `PlayerDoTurn` catches silent free grants/removals. A reentrancy lock suppresses dirty callbacks from the marker setters. `CityCaptureComplete` reacquires the reconstructed city through `Map.GetPlot(x,y):GetPlotCity()`; it never retains a stale city object or old owner/city-ID pair. The capture handler clears foreign-owner effects and recalculates eligible acquisitions. Dummies are independently noncapturable. Initialization cleans foreign leftover real markers.

The context retires prior registered callbacks, removes them where supported and makes any surviving callback inert via controller ownership. Shutdown clears only its own ownership. No frames, polling UI, global city-panel changes or additional external dependencies are introduced.

## Verified CP v151 source contracts

The repository pins [official CP sources at 44c1e14](https://github.com/LoneGazebo/Community-Patch-DLL/tree/44c1e14ff75d80c1dba5c8a71e8289439a53aafb). `tools/validate_rfd.py` checksum-verifies the required source files, then checks:

- `CvPlayer.cpp`: `PlayerDoTurn` dispatch and serialization of `player.m_strScriptData`.
- `Lua/CvLuaPlayer.cpp`: ScriptData methods, Culture hundredths, Gold hundredths read, and `ChangeGold`.
- `Lua/CvLuaGame.cpp`: `GetStartTurn` and `GetGameSpeedType`.
- `CvInfos.cpp`: the actual game-speed column **ConstructPercent** (the request's conceptual “ConstructionPercent”).
- `CustomMods.h`: construction/purchase and sold-building event signatures.

The fixture is a real BNW snapshot plus an explicit CP v151 schema overlay in memory. It proves schema and inherited-value behavior, not activation of the native CP DLL in a launched game. `Validation.json` records this distinction and the executed Lua scenarios. Native acceptance remains in [Testing.md](Testing.md).
